## Findings（Cross-Feature）

### F-T008-1（HIGH）：Spec / quickstart 內 SQL 用錯 column name

- **Symptom**: spec.md 與 quickstart.md 內 SQL 用 `SELECT user_name FROM sys_user`
- **Reality**: 實際 sys_user table 的 column 是 `username`（無底線）
- **Source**: `admin-api/migration/src/schemas/m20240815_082854_create_sys_user.rs`
- **Affected docs**:
  - `spec.md` US1 Independent Test 內 SQL
  - `quickstart.md` §1.3「3 個預設 user」段
  - `tasks.md` T008 acceptance 指令
- **Fix**: 在 follow-up commit 把 `user_name` → `username`（5 處左右）

### F-T008-2（MEDIUM）：第二次 migration 82 秒、超 SC-004 「≤ 5 秒」目標

- **Symptom**: 第二次 `docker compose run --rm migration` 耗時 82 秒
- **Cause**: docker compose run 起新 container、BuildKit cache mount (`/app/target`) 是 build-only directive、不 persist 到 runtime image，所以每次新 container 都要重新 cargo build migration binary
- **SC-004 expectation**: 「migration 第一次跑 ≤ 30 秒、重跑 ≤ 5 秒（idempotent 快路徑）」
- **Mitigation options**:
  - (a) admin-api Dockerfile 把 migration binary 也 COPY 進 final image（feature 6 envsubst 改造時順便處理）
  - (b) 修 SC-004 為「migration logic 上的 idempotent」（不限定耗時）
  - (c) 接受 82 秒 deviation，視為「現實 vs spec」可記錄
- **Recommendation**: feature 6 處理 (a)，SC-004 在 feature 1 maintained as「idempotent verified by application logic」
